# Design guidance

The rules for every tool built on this system. Values live in `tokens.json`; this page says how to use them.

## One base, two projects

This system serves Alon's browser tools that generate printable parts. The **base** (everything outside the two project sections below) is shared: workbench layout, Choice buttons, Fira Code, Codicons, rounded corners, light and dark themes, save and load, live updates. Each **project** adds only its own cover, model colours, step names, wording and a few components. A new generator starts from the base and adds one more section.

A **cover** is fixed-size artwork (960 × 288 px) for use outside the tool: the gallery card, the repository's social preview, a README banner. It does not reflow, so it never appears in the tool itself.

- **Parametric window sealer** (AlonRR/parametric-window-sealer): panels and seals for the gap a window leaves. Model colours `model-panel`, `model-joint`, `model-tape`, `model-tpu`, with `model-outline` edges. Steps: Opening, Window, Fittings, Seal, Printer and style. Cover: `Cover`.
- **Skådis Air** (AlonRR/skadis-air): light, tileable SKÅDIS-compatible pegboards and connectors. Model colours `model-board`, `model-board-outline`. Steps: Board, Size and sides, Mounting, Printer. Components: `Sides`. Cover: `CoverSkadisAir`.

Use `surface` for the page and the stage, `surface-raised` for the header, sidebar, dialogs and groups, and `ink` for text. Put notes, units and errors in `ink-muted` and `error`. Never put `ink-muted` or `error` on a coloured fill.

## The tool is a workbench

- **The wall is the page.** The 3D stage is the biggest thing on screen and is always visible. Controls live in a sidebar beside it. The result is never below the inputs. (See `Workbench`.)
- **The part always fits the stage.** It is framed to fill `stage-fit` of the stage whenever the part or its size changes. When the stage changes size, the camera keeps the user's angle and pulls back only as far as the whole part needs to fit again. Zooming out stops at `stage-min-fill`, and panning cannot move the part off the stage. "Reset view" returns to the first view. A browser test checks the part's outline lies inside the stage on a phone and a desktop, and after a resize.
- **Header, stage, sidebar, status bar.** A slim `header-h` header carries the name, undo/redo/reset, Save project, Load project and the theme toggle; below the breakpoint everything but Undo and Redo sits in one labelled "More…" menu (D28). The stage fills the rest, with a status bar (`status-h`) under it showing sizes, units and a hint naming the gestures the tool supports, one for a mouse ("Left drag: orbit · Scroll: zoom · Arrow keys: turn") and one for a touch screen ("Drag: turn · Pinch: zoom"), never both. Over the view, "Reset view", "Zoom in" and "Zoom out" at the top right and a Front · Back · Top choice at the bottom left (D30); on a phone or a short screen, "Reset view" and "View…", a menu holding the rest, so the view stays clear for pinch and drag (D36). The sidebar is `panel-width` wide; collapsing it from an edge toggle is planned, not yet a component.
- **Light or dark, as the system says, until the user chooses.** The page follows the system setting until the header's "Dark theme" toggle is used (a `button` with `aria-pressed`, pressed while the page is dark). The choice is then remembered in this browser and wins over the system setting; where the browser keeps nothing (a private window), it lasts while the page is open. The theme is set on `<html>` before the page is first drawn, so a dark screen never flashes light, and everything that follows the theme, the 3D view included, watches `data-theme`, never the system setting itself.
- **One form first; numbered steps when it outgrows a screen (D31).** A short tool is one form in the sidebar. A longer one gets a step rail across the top of the sidebar, one step at a time: each step button shows its number and name ("2 Window"), the current one carries `aria-current="step"`, and a done one says "done" to assistive tech. The sidebar shows the current step's title and fieldsets, then Back and Next. The stage shows the whole part at every step and highlights what the step changes. The steps of each tool are in its project section.
- **Open on a working example.** The first visit shows an example wall and says so; presets replace every value in one tap. A short welcome dialog gives a four-step quick start and says everything runs in the browser, then never shows again.
- **Live, no Apply.** Every change updates the stage at once. An invalid value keeps the last good part, marks the field and says what to fix. A build that can take longer than about 100 ms runs off the page's main thread, so typing never stalls; the last good part stays on the stage, with the stage message "Updating…", until the new one is ready.
- **Show only what applies.** Track depth appears only for an edge in a track; hose size only for a hose. Rarely changed settings go in an "Advanced" `Disclosure` at the end of the step.
- **Pick-one options are buttons with a radio mark.** Use `Choice`: every option is a button with a small radio circle at its left. The chosen one is `action-tint` with an `action` ring and a bold label, and its circle holds an `action` dot, so it reads as selected without relying on colour (D26). A tick means pick several (the `Sides` toggles); never use a tick for pick-one. For picture options use `Gallery`, not a dropdown.
- **Projects can be saved.** Save project and Load project write and read one file; undo and redo cover every change.
- **Measuring help is beside the field.** A "How do I measure?" link opens the guide with its drawing as a panel; the user returns to the same spot.
- **Phone:** the 3D view alone is pinned at the top, `stage-phone-h` (45 % of the screen); under it the plan bar, pinned too, is one row: the sentence, at most two lines, beside the primary button, which stays in reach. "Reset view" sits on the view. The status bar and the sidebar scroll beneath. A focused field always lands below the pinned part. A short or zoomed screen (under `breakpoint-short`) pins nothing, and a landscape phone (at least `landscape-ratio`) puts the sidebar beside the stage (D25). Touch targets are `tap` (44px) or more; rotate and zoom use drag and pinch.

## Reference implementations

What a tool needs beyond the stylesheets is code, and the code stays in the tools: this repository holds no TypeScript. Skådis Air built each piece first; the window sealer copies them and renames what names Skådis Air. The links are pinned to `AlonRR/skadis-air` at `b55c32d`, its `main` on 15 Oct 2026.

- **The theme:** [`web/src/theme.ts`](https://github.com/AlonRR/skadis-air/blob/b55c32d/web/src/theme.ts) and the script at the top of [`web/index.html`](https://github.com/AlonRR/skadis-air/blob/b55c32d/web/index.html), the rule "Light or dark" above. The script sets `data-theme` before the page is drawn; `theme.ts` keeps it in step and works the toggle, and survives storage that is missing or refused.
- **The part always fits the stage:** [`web/src/framing.ts`](https://github.com/AlonRR/skadis-air/blob/b55c32d/web/src/framing.ts) works out how far the camera stands so the part spans `stage-fit` of the stage, and where zooming out stops (`stage-min-fill`), from the eight corners of the part's bounding box as the camera sees them; [`web/test/framing.test.ts`](https://github.com/AlonRR/skadis-air/blob/b55c32d/web/test/framing.test.ts) holds both to three.js's own projection. Skådis Air switched panning off, which the rule allows.
- **The workbench's browser test:** [`web/e2e/workbench.spec.ts`](https://github.com/AlonRR/skadis-air/blob/b55c32d/web/e2e/workbench.spec.ts), 8 tests (12 runs, as the four framing tests run on a phone and on a desktop): the part framed to `stage-fit` and inside the stage, pulled back inside after a resize, zoom out stopping at `stage-min-fill`, "Reset view" framing it again, the stage beside the sidebar on a wide screen and on top at 45 % of the height on a phone, and the theme following the system until chosen, then remembered.
- **Copying the system in:** [`scripts/design-system/copy-design-system.sh`](https://github.com/AlonRR/skadis-air/blob/b55c32d/scripts/design-system/copy-design-system.sh) copies `tokens.css`, `components/bundle.css` and `fonts/` from a tag's commit, byte for byte, and checks each file against it; the page serves them unchanged from `web/public/design-system/` (README, "Using it in a tool").

## Rules for changing the system

No value is typed twice. Colours, sizes, gaps, the ring width, the control height and the breakpoint live in `tokens.json`; components read them as variables. Three scripts keep it honest, each held to its own controls in `tests/`. Run them after any change:

- `uv run python scripts/build-tokens.py` rebuilds `tokens.css` from `tokens.json`, works out each font's vertical-centring overrides from its cap height, and fails if `bundle.css` types a value a token holds: a colour in any notation (a system colour and `color-mix()` too), a gradient, a length (beyond a few geometric ones such as `100%`), a font family, size, weight, line height or tracking, an opacity, a custom property `tokens.css` does not define or one it re-sets (only `control-h`, on a touch screen), an at-rule but `@media` and `@supports`, a second breakpoint, or a font of its own (the fonts load once, through `tokens.css`); if a wide-screen rule is undone by a later one; if a grid popover has no `align-content`, which WebKit stretches; and if a type style asks for a weight no font file ships. `tests/test-build-tokens.sh` proves each of these fails.
- `uv run python scripts/check-contrast.py` checks every theme: text pairs need 4.5:1, borders, focus rings and outlines 3:1, and each part in the stage shows against it (3:1) by its fill or its outline, and an open dialog against the page dimmed behind it (3:1) by its face or its edge. It fails on a colour in no pair, so add the pairs when you add a colour; `tests/test-check-contrast.sh` holds it to controls.
- `uv run python scripts/check-previews.py` renders every `preview.html` in every theme on a phone (375px, touch) and a desktop, and the workbench and header on five more screens, and fails if a glyph falls back to another font, the page scrolls sideways or a box cuts off, spills or scrolls its content sideways, a focused control has no `action` ring 2px wide or something clips it, a disabled control changes on hover or an enabled one does not, a selected control is not tinted and ringed with an `action` border and a bold label, a menu (More…, View…) does not open under its header or button, on the screen, the phone's view and plan bar are not pinned, a toggle has no `aria-pressed` or a Choice is no named `radiogroup`, a touch control is under 44px, a run of text, as drawn or hovered, is under 4.5:1 against what is behind it, a class the stylesheet styles is shown by no preview or named in no doc, or a doc names a class the system lacks, two states look the same in forced colours, an open dialog runs to the screen's edge or has no scrim behind it, a control is not `control-h` tall, a label or a Sides tick is more than 1.5px off centre or covered, the chosen Choice is not tinted and ringed with a dotted radio, anything but the primary button is filled with `action`, a Sides box is not the radio's size, an icon reaches an accessible name, a page's `color-scheme` is not its theme, a status bar shows the wrong hint for the screen, a Notice's colours are not its variant's, an empty Notice or stage message takes room, a canvas does not fill its stage view or resizes it, the 3D view cannot be used without a pointer (no focusable, named drawing described by the plan line, no ring inside the view, no Reset view, Zoom in, Zoom out or view choice, controls over each other or swallowing a drag, or on a phone no View… menu opening under its button), or the plan bar's sentence is squeezed below `plan-line-basis`. Write a preview for every new component.
- Every change a tool can see goes in `CHANGELOG.md` under the next version, with how a tool moves to it. The version lives in `tokens.json` and `pyproject.toml` and heads `tokens.css`; the build keeps them, the changelog and the tag in step (D32). While the version is 0.x, a change that breaks a tool's markup or CSS raises the minor version.

Controls are `control-h` tall (36px), and `tap` (44px) on touch screens, set once; inputs, selects, PieceMap cells and Disclosure summaries are at least that tall. Focus, selected outlines and the chosen radio's ring all use `ring`; the radio's offsets are derived from it, so changing `ring` or `radio-size` cannot shift a label. Icons, ticks and radio marks sit `icon-gap` from their label.

## Content fundamentals

- Say "you" and use plain words: panel, piece, strip, edge, seal. No jargon.
- Units in every label: `Width (mm)`. Metric by default, millimetres for sizes. Imperial stays available as a setting next to language, for people who read inches more easily (D33).
- Be honest about what is untested: the joint fit and track sizes are "starting values that a test print still has to confirm". Put it in a note, not a tooltip.
- Errors say what to fix: "Fix the marked fields to see the plan." Warnings name the choice that resolves them.
- Sentence case for headings and buttons. End a button that opens a dialog with an ellipsis ("Download the pieces...").
- Say where the work happens: "Everything runs in your browser; nothing is uploaded."

## Visual foundations

- **Quiet, light and soft-cornered.** Light surfaces, a hairline `divider` between regions and `border` round groups, one accent. Corners are rounded: `radius-sm` (8px) on buttons, inputs, tiles and notices; `radius-md` (14px) on groups and dialogs. No shadows, no gradients, no motion.
- **One filled colour.** `action` fills only the primary button, so the one filled thing on a screen is the next step, and draws the focus ring (solid 2px, 2px offset). Every selected state is `action-tint` with an `action` ring: the chosen Choice, a pressed Sides toggle and the active step, in bold, and a selected tile or piece (D26). The marks inside them, the radio's dot and the Sides box, are the only other `action` fills. `error` outlines a field and the message explains it. Colour is never the only signal.
- **Control borders are `border-strong`** (3.5:1 or more); `border` and `divider` only separate.
- **The `model-*` colours are materials in the stage**, not UI: never use them for text, borders or a control's own fill; a drawing of the part, such as a `Gallery` tile, may use them. `model-tape` orange means seal.
- Section labels in the sidebar use `.ws-caps`, the `label-caps` style (uppercase, tracked, `ink-muted`). The status bar takes the same size in normal case, so its hints read as sentences.
- Guide drawings are inline SVG in `currentColor` with arrow markers.

## Type

One family for everything: FiraCode Nerd Font (`ui`), a monospace face with icons built in. Fewer typefaces keep the interface calm, and a fixed-width face lines numbers up in columns and keeps 0/O and 1/l/I distinct. Do not mix in another family. Hierarchy comes from size and weight, never a second face. Styles: `title`, `section`, `step`, `body`, `legend`, `note`, `label-caps`, `code`. A page of text goes in `.ws-text` (body type, at most `measure` wide). Text is 15px (`body`) and notes 13px; keep notes to short sentences, since a monospace line holds fewer characters.

Vertical centring is fixed at the font, not per component: the `@font-face` rules in `tokens.css`, written by `build-tokens.py`, set `ascent-override` 96.85% and `descent-override` 26.23% for Regular (97.08% and 26.00% for Bold; line gap 0), computed from each font file's cap height so capital letters sit on the centre line of any line box. Any new font needs its own pair (ascent minus descent equals cap height; ascent plus descent keeps the line height). Do not nudge text with padding.

Ligatures: on in text (so `=>` and `->` join), off in inputs, numbers, file names, the status bar and the plan line (`ws-input`, `code`, `ws-num`, `.ws-status`, `.ws-plan__line` turn them off, and a check holds it: D29), so a value never changes shape. Use real arrows (→) in labels, e.g. "Next: Fittings →". Numbers use the slashed zero.

## Accessibility

- Native elements: `fieldset`, `legend`, `details`, `dialog`, `select`. Pick-one options are radios underneath, shown as `Choice` buttons; the picture and map pickers (`Gallery`, `PieceMap`) are buttons with `aria-pressed`, one pressed at a time. Every control has a visible label.
- State never relies on colour alone: errors have text, the active step has `aria-current="step"` and a ringed, bold button, selected tiles use `aria-pressed`. In forced colours (Windows High Contrast and the like) the browser keeps only the user's system colours, so the stylesheet uses them, there alone, to keep each state its own look: the chosen radio a filled circle, a step not reached without the border of a done one.
- Announce changing results (the plan line, errors, download status) with `aria-live="polite"`. Keep an empty live region in the page, collapsed, never `display:none`, so it is announced when it fills. Link a field's error and note to it with `aria-describedby`.
- The stage works without a pointer (D30, WCAG 2.1.1 and 2.5.7): every move is a press (Reset view, Zoom in, Zoom out, Front · Back · Top; on a phone the last four in the View… menu), and the focused view, ringed inside its edge, turns with the arrow keys and zooms with + and −. It is an image named for the part ("The wall in 3D") and described by the plan line, its text equivalent, which says pieces, ports and seal.
- Numeric fields: `inputmode="decimal"` for a value that cannot go below zero, `type="number"` for one that can (the decimal keypad on a phone has no minus sign); "," is read as a decimal point as well as ".".

## Iconography and logo

Icons are Nerd Font glyphs. Prefer the thin-line Codicons (`cod-`), which are the lightest weight here, and use one set throughout (see `Icons`); Font Awesome (`fa-`) is solid and heavier. Real Regular and Bold weights are bundled, so bold text is a true bold: `<span class="ws-ic" aria-hidden="true">&#xeb4b;</span>Save`. Every icon sits before a text label and is `aria-hidden`; an icon is never the only thing that says what a button does. Common ones: save eb4b, load eaf7, download eac2, undo eae2, redo ebb0, reset eb37, theme eac6, tick eab2. There is no logo; the tool name is set in the `step` style.

## Project: Skådis Air

- **Voice.** Short and plain, like the page: "Download STL", "Reset view", "= 6 tiles". Say what is untested: every number marked "to confirm" is a starting value until the fit coupon has been printed. Sizes in mm, in 40 mm steps, with the tile count beside the field.
- **Steps.** Board (solid, lightened or skeleton; list only the types that are built), Size and sides, Mounting (screw holes in the corner tiles, countersunk by default; optional 20 mm standoffs on the back), Printer (bed 200 × 200 mm by default, custom size beside it).
- **Stage.** The board is shown as it hangs: upright, front toward you, slots vertical, in `model-board` with `model-board-outline` edges. Drag turns it, wheel or pinch zooms, "Reset view" returns. One "Download STL" button sits under the preview.
- **Sides.** Open or closed is chosen side by side with `Sides`: four toggles round a small drawing of the board. A single panel is open all round by default; a wall is closed round its outer edge.
- **Advanced.** Slot clearance, chamfer and corner radius are folded under an "Advanced" `Disclosure`.
- **Warnings.** A board larger than the bed, or a thickness outside 4 to 5.5 mm, shows a `Notice` in `warning`. It warns and never refuses.
- **Brand.** Say "SKÅDIS-compatible". The page carries the line that it is not made, endorsed or supported by IKEA; no IKEA logo, colours or wordmark.

## Project: Parametric window sealer

- **Voice.** Panel, piece, strip, edge, seal.
- **Steps.** Opening, Window, Fittings, Seal, Printer and style. `model-tape` orange means seal.
- **Stage.** The wall seen from the room, with `PieceMap` to pick one piece.

## Where this comes from

Window sealer: the model colours (`model-panel`, `model-joint`, `model-tape`, `model-tpu`), `error` (#b00020) and once `choice` (#b06d00, dropped in D27, as every Choice has a default), the units, the form wording and the part vocabulary come from the repo AlonRR/parametric-window-sealer (main@1b47d3a), whose page is a single plain column with the result at the bottom. Skådis Air (AlonRR/skadis-air, then named skadis_ultralight_generator, main) adds `model-board`, `model-board-outline` and `warning`, and its decisions D37 to D75 supply the sides, size and mounting behaviour. This system replaces both pages' layouts and styling. The direction (stage-first workbench, header toolbar, 380px sidebar with a numbered rail, status bar, texture-style gallery, save/load project, rounded corners (8px and 14px), one Nerd Font (FiraCode), a restrained blue accent) follows the CNC Kitchen apps (BumpMesh, filaSim) as seen on cnckitchen.com/tools; it uses their approach, not their logo or brand marks. Colours here are chosen for this project and checked for contrast; sizes are this system's own. The dark theme is an addition. Components are hand-written; the repo has no component library, so there is no code bundle.
